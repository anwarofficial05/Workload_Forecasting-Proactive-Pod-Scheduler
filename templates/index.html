1. Problem Definition (Zeroth Review)

Cloud applications receive different amounts of user traffic. The default Kubernetes scheduler reacts only after CPU or memory usage becomes high. This causes response time delays and reduces performance. Single-metric, threshold-based logic cannot anticipate bursty traffic patterns or balance multiple competing objectives across worker nodes.

Limitations of Existing System: Reactive scheduling, No workload prediction, Higher response time, Poor resource utilization, Uneven workload distribution.

2. Proposed System & Novelty

Our project combines LSTM (capturing long-term temporal dependencies) and XGBoost (capturing non-linear feature interactions and sudden spikes) to forecast near-future workload. Candidate worker nodes are then scored and ranked using Multi-Objective Node Ranking (MONR) based on CPU, memory, latency, and balance. The pod is placed proactively on the best node before traffic surges occur.

Literature Review & Core Research Gap

Base Paper 1: Amirullah & Saikhu (IEEE IAICT 2025)

Validates that LSTM outperforms ARIMA and GRU for CPU usage forecasting with lowest MSE (0.00001053) using Beta synthetic traffic. Gap: Stops at forecasting CPU only; does not connect prediction to pod scheduling decisions.

Paper 2: Matsiievskyi et al. (SIST 2025)

Used LSTM for server load forecasting, identifying sudden-spike prediction lag as a fundamental limitation of pure LSTM. Our Solution: We integrate an XGBoost regressor into an ensemble to capture sudden spike rates of change.
